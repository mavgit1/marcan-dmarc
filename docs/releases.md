# Releases

Newest first. Each release is tagged `vX.Y.Z` and the image `ghcr.io/mavgit1/marcan` carries the same tag; how to move to a new one is in [Upgrade](./upgrade). An entry says what changed and what, if anything, to do before upgrading.

## 0.4.0

Before upgrading: take a [database backup](./backup#the-database-file). The migrations of this release are one-way: 0.3.x refuses the migrated database, so the way back is that backup (see [Going back](./upgrade#going-back-to-an-older-version)), and credentials encrypted with `MARCAN_SECRET_KEY` need that key too. The first start rewrites the database file once (to remove the old unencrypted passwords from it), which needs as much free disk space as the database takes. Nothing else to do: with Report delivery set to forwarded, the addresses your domains' DMARC records name are entered on the first account as its forwarded addresses.

- **Accounts**: Settings → Accounts replaces Settings → Mailbox, and every mailbox and SMTP login is now a mail account: one credential at one provider (any IMAP/SMTP server, Google with an app password, or Microsoft 365 with a Microsoft login), with its address, login, receiving folder and any number of forwarded addresses, its servers under Advanced (none for Microsoft 365), a Test of its login and mailbox (no message sent) and Delete. Each card shows the address, whether reports land there, whether Sending uses it, its last check, any credential warning, and a warning when two accounts read the same mailbox and folder; the schedule and the report arrival warnings sit below the cards. The upgrade converts the mailbox into the first account (the report address onto it) and a sending login of its own into a second. `/settings/mailbox` leads to the new page. See [Accounts](./accounts).
- **Several mailboxes**: reports arrive in any number of accounts, read one at a time in turn; a long first import gives way to the others after 2 minutes and resumes. An account that keeps failing (unreachable server, refused login or Microsoft token) waits longer each time, from 30 seconds up to an hour; saving it, Sync now, Re-import or Test start over. Sync now and Re-import read every receiving account, the header sums them up, and client reports are held while any of them has not been read for 3 days. See [Several accounts](./accounts#several-accounts).
- **Microsoft 365 mailboxes** work with an app registration in Microsoft Entra, proved with a certificate Marcan generates, and Exchange Online roles that give it the one mailbox: Marcan reads reports and sends as the mailbox over Microsoft Graph with OAuth 2.0 tokens, which it keeps in memory and sends to Microsoft Graph only. The account has no servers. The account's Test checks the token, then reads the mailbox and lists its folders, and says what to change in Entra or Exchange Online; sending is tested by the Sending page's test message. A new alert, **Microsoft certificate expiring** (Settings → Alerts, group Accounts), says so 30 days before the certificate expires, and again once it has expired. Tokens are renewed when Graph refused one, after the host slept, and with at least 20 minutes left before a mailbox read; two accounts sharing one app registration keep their own. When Graph refuses a message, the message says why: the app not allowed to send as the mailbox, throttling or a message too large. See [Microsoft 365](./accounts#microsoft-365) and [Alerts](./alerts#what-is-alerted).
- **Secrets at rest**: with `MARCAN_SECRET_KEY` set (generate it with `openssl rand -base64 32`), Marcan stores the accounts' passwords and certificate keys encrypted (AES-256-GCM), and its first start with the key encrypts those already stored and removes their old unencrypted values from the database file. Keep the key apart from the backups; `MARCAN_SECRET_KEY_FILE` reads it from a file (a Docker secret), which keeps it out of `docker inspect`. To change the key, set the old one as `MARCAN_SECRET_KEY_PREVIOUS` beside the new one and restart once. Without the key nothing changes. A missing or changed key locks the accounts it cannot read until the key is restored or their credentials are entered again, a damaged stored value says so, and a malformed key stops the start. The Compose stacks pass the variables on, commented out in `.env.example`. See [Secrets at rest](./security#secrets-at-rest).
- **Report addresses per account** replace the central and forwarded Report delivery modes: reports reach Marcan at each receiving account's address and at the addresses forwarded to it (any number per account, each on one account only, so an MSP can list one forwarder per client). A domain's DMARC record is set up when it names one of these and that address's domain accepts the domain's reports (or needs to accept nothing, being under the same organizational domain); new records name the first receiving account's address. The authorization is checked per address domain, wildcard included. An upgrade from forwarded mode puts every address your domains' records named at the last DNS check (other than the mailbox's own) onto the first account, so those domains stay set up. See [The report address](./accounts#the-report-address).
- **The setup** now goes organization, accounts (one or more, each tested before it is saved; an account with a newly generated certificate is saved first, then the certificate is uploaded and tested), import (per account), domains, report addresses (every address with the authorization records it needs, nothing to type), DMARC records, done. Links to the old Mailbox and Report delivery steps open the new ones.
- **The Guide** opens with where reports reach Marcan ("Reports reach Marcan at …, forwarded from …") and how many domains report there, or "No account receives reports yet" with a link to Accounts, then each receiving domain's permission to receive reports.
- **Settings → Sending** chooses the account mail goes through ("Reports (smtp.example.com)") and always sends from its Email address; the SMTP server and login fields moved to the account. A sender address saved separately under Sending is gone after the upgrade, and mail comes from the account's address: to send from another address, add an account with the same login, that address as its Email address and receiving off, and choose it under Sending. If sending had its own SMTP login and used the report mailbox's address as sender, the Sending account has no address after the upgrade and cannot send until you give it one of its own under Accounts (two accounts cannot share an address); Settings → Sending says so. See [Sending](./accounts#sending).
- **Client reports** are held while any receiving account has not been read for 3 days, counted for a new or changed account from when it was saved, and the held line names that account. A mail server refusing the sending account (such as Exchange's send-as refusal) no longer counts as every recipient refusing the report: it is retried like any passing failure and listed as "sending account refused".
- New alert, **Account not read** (Settings → Alerts, group Accounts): a receiving account not read for 3 days, with the reason (locked credentials or the last error); the same rule holds the client reports. See [Alerts](./alerts#accounts-not-read).
- An empty IMAP or SMTP port on an account is the provider's usual one for the security chosen, for the save, the test and sending alike. An account with a password login needs an IMAP or an SMTP server.
- `--secret-key` is gone (it showed the key in the process list): use `MARCAN_SECRET_KEY` or `MARCAN_SECRET_KEY_FILE`.
- Messages the import gave up on under a mailbox configured before the current one are no longer counted. The JSON API (internal) changes: `/api/accounts` and `/api/settings/receiving` are new, the mailbox, reporting and IMAP connect endpoints are gone, and the settings, sending and health answers change shape. The CSV exports change only as listed below.
- CSV exports refuse a query parameter they do not read (such as `domain=` for `domain_id=`) with a JSON `400` naming the ones they take, instead of ignoring it and exporting every domain. See [Automating](./exports#automating).
- While an import is unfinished, also between the passes of a long one, the header and the Guide say "Importing" (with the messages left while a pass downloads) instead of "Up to date".
- **Policy readiness** no longer needs 200 messages: 30 days of reports are what a small domain can show, so a domain with a handful of messages, all passing, is ready, and the verdict says how many messages it rests on. Domains that were "too little mail" can become ready after the upgrade, each with its "Ready for…" alert. A new rule holds a domain back while more than 10% of its passing mail passed DMARC on SPF alone, without an aligned DKIM signature, since that mail fails once it is forwarded; the Enforcement tab shows the share and says what to sign, and a domain called ready before can be not ready after the upgrade. See [Policy readiness](./readiness).
- **Alerts**: delivered failures opening or clearing together with a health change is one "Health changed" alert instead of two (if you muted "Health changed" but not the delivered-failures alerts, that email no longer comes), and new failing senders are judged by network (/24 for IPv4, /48 for IPv6): an address in a network that already sent as the domain is not new, and several new addresses of one network are one alert. See [Alerts](./alerts).
- A domain's page shows one DNS check: the header's policy, the readiness line, the Enforcement tab, the DNS checks and the "Reports don't reach Marcan yet" card read the same stored check, and the one Re-check DNS updates all of them.
- The **Failures** tab shows when each row was seen and links to the newest report with it; a report's records show the envelope sender where it differs from the From domain.
- **domains.csv** has a new column, `readiness_reason`: why a domain is not ready for its next policy step, or not judged. See [Exports](./exports).
- Health's best state is now called **Healthy** instead of Protected, on every page, in the alerts and in the emails: it says the delivered mail is authentic, not that spoofing is stopped (a `p=none` domain can be healthy). In **domains.csv** the `health` column reads `healthy` for it instead of `protected`. See [Health](./dashboard#health).
- Alert kinds (Settings → Alerts) each say in one short sentence what triggers them, the group Readiness is now Enforcement, and how alerts are counted is in the [docs](./alerts). A cleared delivered-failures alert says it is back under the threshold ("Delivered failures back under 1%: …"), and a policy change names the tags as the record writes them (`p=none → p=quarantine`).
- The organizations list keeps its columns aligned whatever the organization names.
- **auth-issues.csv** has a new last column, `envelope_to`: the recipient domain, where the reporter names it.
- Docs: a new [Accounts](./accounts) page replaces Mailbox & reporting setup (the old address points there), with the Microsoft 365 steps in Entra and Exchange Online PowerShell, Google app passwords and the report addresses; [Secrets at rest](./security#secrets-at-rest) in full; the setup, the FAQ, How it works, the roadmap, Backup, Deployment and the stack pages updated; new screenshots of Accounts, an account, the setup and Sending.

## 0.3.2

Before upgrading: take a backup if you want to be able to go back, since this release has a database migration (the alert events table gains installation-wide events) and 0.3.1 cannot open the migrated database. Nothing else to do.

- New alert, **Update available** (Settings → Alerts, group Updates): while the daily version check is on, a release newer than the running one is one alert, "Marcan 0.3.2 is available.", linking its release notes in the Alerts list, the alert email and the digest; once per version, and the first look after upgrading is its starting point. See [New releases](./alerts#new-releases).
- **Import hardening**: the reports of one mailbox message share a 50 MiB budget after decompression; an attachment past it is refused and the message quarantined, and a batch is stored early once it holds 16 MiB of reports. A crafted message could otherwise have taken the whole import down. See [Security](./security).
- **Login stacks**: the OAuth2-Proxy stack now sets `OAUTH2_PROXY_PROVIDER=oidc`; before, every sign-in went to Google whatever issuer was configured. Its cookie-secret command now produces a value OAuth2-Proxy accepts. The Authelia stack stops logging a timeout for every idle connection. Fetch the stack files again when you use one of them.
- **Settings → License** (About) links "Report a bug in 0.3.2" beside the running version, to the [GitHub issues](https://github.com/mavgit1/marcan-dmarc/issues).
- Docs: the deploy pages fetch their files from `main` (always the latest release) instead of a tag; the Authelia page spells out the first sign-in with a second factor; the [FAQ](./faq#how-do-i-report-a-bug) and the README say how to report a bug.

## 0.3.1

Nothing to do before upgrading. Every domain is re-checked once after it.

- The Compose stacks run `ghcr.io/mavgit1/marcan:latest`, and `MARCAN_VERSION` is gone from them and from `.env.example`. An upgrade is `docker compose pull && docker compose up -d` after reading this page; to pin a version, edit the `image:` line. Files fetched before keep reading `MARCAN_VERSION` from your `.env`; with the new files it is ignored. See [Upgrade](./upgrade).
- **Guide** under Tools replaces the read-only Setup: how reports reach Marcan, the mailbox domain's permission, what Marcan judges, enforcement, alerts and client reports, each with this installation's values, where it stands and a docs link. The setup's first step no longer opens with an intro.
- DMARC checks read RFC 9989's `psd=` tag: `y`, `n` and `u` no longer show as an unknown tag, another value is a warning (`dmarc_bad_psd`). See [DNS checks](./dns-checks#dmarcbis-rfc-9989).
- Turning DMARC testing mode (`t=y`) on or off is a **DMARC policy change** alert, like a new `p=`, `sp=` or `pct=`: "DMARC policy changed: testing mode on (t=y)." On under quarantine or reject is amber, off green. See [Alerts](./alerts).
- While the version check names a newer release, the header shows "0.3.1 available" beside the status, linking its release notes.
- Docs: the [Pricing](./pricing) page shows the plans as cards with their checkout buttons (prices and terms unchanged); the deployment stacks sit in a collapsible group in the sidebar; [Backup](./backup) and [Upgrade](./upgrade) are shorter and start from starting over with the mailbox and the four lists.

## 0.3.0

Before upgrading: take a backup. This release has the first database migrations (new columns on the DNS snapshots) and re-checks every domain once; the default Compose stack moved to `deploy/caddy/`, see the first note. A database opened by 0.3.0 cannot be opened by 0.2.1 again.

- **The default Compose stack moved from `deploy/` to `deploy/caddy/`**, beside `deploy/authelia/` and `deploy/oauth2-proxy/`; the files changed only in their comments. If you downloaded the files into a directory of your own, as the guide says, nothing changes: fetch them from `deploy/caddy/` from now on. If you ran the stack from `deploy/` in a clone, Compose would take the new folder's name as the project name and start with a new, empty volume: before `docker compose up -d` in `deploy/caddy/`, move your `.env` (and `data/`, with a bind mount) there and add `COMPOSE_PROJECT_NAME=deploy` to `.env`, so the volume `deploy_marcan_data` is found again. See [Caddy with basic auth](./deploy-caddy#upgrade).
- The docs have a page per deployment stack ([Caddy](./deploy-caddy), [Authelia](./deploy-authelia), [OAuth2-Proxy](./deploy-oauth2-proxy)), each with every file, the `.env`, the login and the first start, and a page for [Policy readiness](./readiness), which moved out of Reading the dashboard. New screenshots of the setup, Settings, the Alerts list and a client report.
- A [Pricing](./pricing) page in the docs, with the two operator plans, the trial and what a key changes; the License page keeps the license and the key's mechanics.
- The emails' letterhead puts your logo left of your name in one row, vertically centred, instead of above it (with an operator key) or inline with the text (without one).
- DMARC checks read the tags of RFC 9989 (DMARCbis): `t=` and `np=` no longer show as unknown tags. `t=y` with an enforcing policy is critical, like `pct=0`, and policy readiness asks you to remove it before the next step. `pct=` below 100 and the obsolete `rf=` and `ri=` get an Info finding each. See [DNS checks](./dns-checks#dmarcbis-rfc-9989).
- Every domain is re-checked once after the upgrade (shown as **updating** until then). The database gains two columns; nothing to do before upgrading.
- `domains.csv` has two new columns at the end: `policy_source` (why the policy columns are empty, if they are) and `readiness` (the domain's policy readiness). The existing columns keep their positions. See [Exports](./exports#columns).
- A daily check for new versions under **Settings → License** (About), on by default: once a day the server fetches a small version file from marcan.kaitiaki.tech (GitHub Pages), carrying no data about the installation, and the page and the sidebar name a newer release. A database from 0.2.1 has no setting for it yet, so the check is on after the upgrade; switch it off there if the server should not reach the internet for it. See [Upgrade](./upgrade#checking-for-new-versions).
- New alert, **New failing sender** (Settings → Alerts, emailed by default like every new kind): a sender new to a domain fails DMARC for it with at least 10 messages in the last 30 days, forwarded mail not counted. Once per domain and sender; the first look after upgrading is its starting point, so the upgrade raises none. See [New failing senders](./alerts#new-failing-senders).
- Client reports read as figures: one line per domain with its policy, its messages, the share that passed DMARC and the failures delivered, blocked and forwarded, plus the step it can take now ("ready for p=quarantine") and the issues no figure shows. The per-domain blocks, the impact line and the "protected and unchanged" line are gone. See [What the email contains](./client-reports#what-the-email-contains).
- The client report recipients list works like the Domains list: it opens with every organization, `Acme,none` for one without a recipient, and saving changes only the organizations in the text (`none` stops an organization's reports). Before, saving replaced the whole list, so a line left out stopped that report. See [Who gets it](./client-reports#who-gets-it).
- The setup's first step opens with how reports reach Marcan, in four sentences. **Setup guide** under Tools is now **Setup**, and the foot of the sidebar shows the running version with a link to the docs.
- Settings → Client reports says, while Branding has no name and no logo, that the reports carry Marcan's letterhead until you set them, with a link to Branding.
- The dashboard's "more need attention" link opens the Domains page filtered to the domains with an open issue, in the attention list's order with their issues first, under a clearable **Needs attention** chip, instead of the list sorted by DNS grade. See [The attention list](./dashboard#the-attention-list).
